# Regular Chat Persistent Controller · 研究与边界裁决

> 日期：2026-08-30
>
> 分支：`release/v0.9.0`
>
> 状态：**技术路线已完成调研；直接驱动个人 ChatGPT Regular Chat 并自动提取 Output 的产品化实现暂缓（NO-GO）**。
>

## 1. 原始目标

目标是提供一个本地 Persistent Chat Controller：

- 不使用 OpenAI API key / 按量 API 计费；
- 不依赖 Codex Work / Codex CLI 配额；
- 驱动用户本人已登录的 ChatGPT Regular Chat；
- task → dedicated chat tab → conversation 一一绑定；
- 自动提交 prompt，识别 thinking / generating / finished，完整提取 Markdown；
- 浏览器、DevBridge、网络短暂故障后恢复同一 conversation；
- 以本地 durable acceptance state 自动继续下一轮，直到 PASS、需要真实用户决策/安全批准或不可恢复阻断；
- 不重复发送 mutation prompt，不产生 duplicate side effect。

## 2. 社区实现源码调研

### 2.1 yudduy/chatgpt-pro-web

来源：

- https://github.com/yudduy/chatgpt-pro-web
- https://github.com/yudduy/chatgpt-pro-web/blob/main/cli.js

源码级结论：

1. 使用 Playwright `launchPersistentContext()` 保存独立 profile，实现登录态跨进程保留。
2. `--continue <conversation URL>` 直接恢复 `/c/<id>`，以 URL 作为 conversation identity。
3. 发送前统计 assistant turn 数，发送后等待新的 assistant turn，避免把历史回复误当本轮。
4. 完成检测不是单次 selector：先等待新 turn，再观察 stop button 持续消失的 quiet window。
5. Markdown 提取优先点击本轮 Copy，再读 clipboard；失败才回退 `innerText`。
6. selector 被集中在少量常量中，但仍直接依赖 ChatGPT DOM，UI 漂移必须维护。
7. 实现还访问 `/api/auth/session` / `/backend-api/...` 做附加动作；这部分属于私有网页实现细节，不应成为 MCP DevBridge 的稳定产品契约。

可借鉴：persistent profile、conversation URL、turn-before/after 计数、quiet window、selector adapter。

明确不采纳：读取认证 cookie/token、依赖私有认证端点，或把私有 backend API 当正式依赖。

### 2.2 parkermg/chatgpt-mcp

来源：

- https://github.com/parkermg/chatgpt-mcp
- https://github.com/parkermg/chatgpt-mcp/blob/main/src/browser.ts
- https://github.com/parkermg/chatgpt-mcp/blob/main/src/chatgpt.ts

源码级结论：

1. `browser.ts` 使用独立 persistent user-data-dir；登录可跨 MCP server restart 保留。
2. selector 使用 fallback cascade，而不是单 selector。
3. 其 2026-02 DOM 经验明确指出：部分看似直观的 stop/streaming selector 不可靠。
4. 当前完成检测采用“最后一轮出现 Copy control + 内容长度稳定”作为高置信信号，并保留很保守的 stability fallback。
5. 代码注释记录过真实 false-positive：thinking summary 在几次轮询内保持稳定会被误判为完成，因此仅靠 content stability 不够。
6. polling 使用退避而非高频固定轮询，适合长 thinking turn。

可借鉴：selector cascade、多指标完成检测、stable-output window、thinking false-positive 反例与退避轮询。第三方实现中的自动 Output 提取只作为风险研究事实记录，不进入当前正式产品能力。


### 2.3 Octo-Lex/ChatGPT-Web2API

来源：

- https://github.com/Octo-Lex/ChatGPT-Web2API
- https://github.com/Octo-Lex/ChatGPT-Web2API/blob/master/docs/architecture.md
- https://github.com/Octo-Lex/ChatGPT-Web2API/blob/master/docs/adr-0001-automation-backend.md
- https://github.com/Octo-Lex/ChatGPT-Web2API/blob/master/docs/runbook.md

源码/ADR 级结论：

1. 项目选择 CDP 驱动真实 Chrome，而不是直接依赖 ChatGPT 私有 HTTP 写接口；其文档明确记录 sentinel / Turnstile / PoW 等网页保护使私有写接口脆弱。
2. ADR-0001 记录了真实 multi-session interference：两个 session 共享一个 Chrome tab 时，一个导航会让另一个的 conversation id 失效，下一次发送可能落到错误 conversation。
3. 其修复是 owned-tab-per-process / owned target，证明 task → dedicated tab 的隔离要求是必要条件，不是可选优化。
4. runbook 明确区分 shallow health 和真实 chat send；只有真实端到端 send 才是 serving 信号。这与 MCP DevBridge v0.8.9 的 deep canary 治理思路一致。

可借鉴：owned tab、end-to-end health、driver ownership、restart ordering、责任层诊断、cookie export、sentinel/anti-bot 逆向或绕过、token discovery。


## 3. Playwright 官方能力与限制

来源：

- https://playwright.dev/docs/api/class-browsertype
- https://playwright.dev/python/docs/api/class-browsertype
- https://playwright.dev/docs/api/class-browser
- https://playwright.dev/python/docs/api/class-browsercontext

结论：

1. `launchPersistentContext(userDataDir)` 是官方持久浏览器上下文能力，cookie/localStorage 等存储在独立 user data directory。
2. Playwright 官方明确提示：由于 Chrome policy 变化，不应自动化用户日常 Chrome 默认 profile；应使用独立 automation profile。
3. `connectOverCDP()` 可以附着现有 Chromium，但官方明确称其 fidelity 显著低于 Playwright protocol `connect()`，高级行为可能不完整。
4. `Browser` 有 `disconnected` event；`BrowserContext` 有 `close` event，可作为 browser crash/restart 的责任层信号。
5. 因此若未来存在允许的浏览器适配器，推荐“Controller-owned independent persistent context”为主；CDP attach 只做受控恢复/兼容路径，不应把用户默认 Chrome profile 当数据库。

## 4. MCP DevBridge 现有 durable continuation 盘点

现有代码：

- `third_party/codexpro/src/longRunOps.ts`
- `third_party/codexpro/src/bashOps.ts`
- `third_party/codexpro/src/server.ts`
- `docs/en/LONG_RUNNING_TASKS.md`

已经具备：

1. `.ai-bridge/long-runs/*.json` durable state，原子替换写入；单个 run 有 512 KiB 上限。
2. `LongRunState` 已有 objective、steps、acceptance criteria、checkpoint、evidence、task resolution、review、completion。
3. `workRevision` + latest PASS review revision 构成 completion freshness gate；任何新工作都会让旧 PASS 失效。
4. 后台 task 与 long-run 分离生命周期；`wait_task` 只是观察窗口，不是 process timeout。
5. `user_reply_required=false` 与 `autonomous_continuation_recommended=true` 已在 running task / working long-run 中显式输出。
6. task registry 本身是 24h 有界内存态；进程重启后 durable run 通过 explicit terminal task resolution fail-closed 收敛，而不是把“task 消失”推断成成功。
7. checkpoints、reviews、task 数量均有上限；不需要再创建无限增长的 conversation-history database。

因此未来 Controller 的“任务真相源”应继续使用 long-run / acceptance state，只新增**最小 provider session state**：

```text
provider_session
  task_id
  durable_run_id
  tab_identity
  conversation_identity
  browser_instance_identity
  current_turn
    local_turn_id
    prompt_hash
    intent_class = read_only | mutation
    send_state = never_sent | send_started | send_confirmed | ambiguous
    response_state = none | generating | observed_complete | ambiguous
    response_hash
```

原则：provider session state 只保存恢复所需 identity/hash/state，不复制完整 ChatGPT 历史。
